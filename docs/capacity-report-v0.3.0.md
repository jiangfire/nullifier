# 容量报告 · v0.3.0（T27）

> 这份报告回答一个具体问题：**「多少投票规模配多少资源」**。
> 数字全部来自**真实投票路径**的压测：真 Groth16 证明（服务端真验签）、
> 资格证明领取（一人一票，与 release 模式同一条链路）、**真 PostgreSQL**。
>
> 复现方式：`bash ./scripts/capacity-run.sh setup` → `sweep`（见文末「怎么复现」）。

---

## 1. 结论速览

- **投票服务不是算力密集型服务。** 实测投票窗口内投票服务只用到约 **1 个核**，
  数据库最多 **11 条连接**、**零锁等待、零 IO 等待**。
  真正的算力大头在**投票人自己的浏览器**上：每张票要出一次 Groth16 证明
  （实测 24ms），服务端只需验签（0.8ms）—— **服务端的算力需求比客户端低约 30 倍**。
- **单机实测吞吐约 2300 票/秒**（并发 50 时；并发 100～200 持平在 2150～2170）。
  按这个数字，**一台 4 核 8G 的机器能扛住十万级选民在 2 小时内投完**（需要约 14 票/秒）。
- **所以规模化的顺序是**：先确认「浏览器出证明够快」（现代笔记本都是毫秒级），
  再按「投票窗口的峰值请求数 ÷ 单实例吞吐」算实例数，最后才是加机器。
  **绝大多数部署根本用不到第二台投票服务。**
- **真正会咬人的是配置，不是算力**：
  - **限流额度**按峰值配（默认 10 rps 会把集中投票挡在门外）；
  - **数据库连接池**要显式配，且**不要开大**（见 §5.3）；
  - **凭证池槽位数**要 ≥ 投票人数（一人一票，领不到就是投不了）。

| 项 | 值 |

| CPU | Intel Core i7-14700F（8 P 核 + 20 E 核，28 线程） |
| 内存 | 32 GB |
| 操作系统 | Windows 11（10.0.26300 x64） |

| 客户端 | `cmd/loadtest`（**与服务端同机** —— 这是最重要的偏差，见 §7） |

## 3. 测量方法

**跑的是真实投票路径**，没有一处占位：

| 阶段 | 内容 |
|---|---|
| 领凭证 | 资格挑战 → 预留槽位 → 盲签名 → attest（**4 个公开端点**，服务端真验资格证明、真盲签） |
| 出票 | 客户端本地加密选票、派生 nullifier、出 Groth16 证明（**7917 条约束**） |
| 投票 | `POST /api/v1/proposals/:id/votes`（服务端真验签、真防重投） |
| 防重投复核 | 同一 nullifier 并发投 5 次，必须**恰好放行 1 个** |

**方法上的三条硬要求**（都是踩过坑才写下来的）：

1. **每轮至少 500 张票**。并发 100 时只有 200 张票的话，每个 worker 只投 2 张，
   测量窗口会被「建连接 + 预热」吃光 —— 实测吞吐从 2300/s 掉到 **127/s**，
   看起来像服务端扛不住，其实是测量方法错了。
2. **每轮之前先热身一轮**。服务端刚启动后的第一轮是冷启动（数据库连接刚建、
   页缓存是冷的），数字不代表稳态。
3. **限流额度要拉高**（压测时 10 万 rps）。否则量到的是限流器，不是服务端。

## 4. 数字

**并发扫描**（每轮 500 票，真证明、真资格、真 PostgreSQL）：

| 并发度 | 吞吐（票/秒） | p50 | p90 | p99 | 最大 | 状态分布 |
|---|---|---|---|---|---|---|
| 1 | 300.8 | 3.08ms | 4.15ms | 5.77ms | 14.80ms | 201 × 500 |
| 5 | 851.4 | 5.79ms | 7.24ms | 7.92ms | 9.42ms | 201 × 500 |
| 20 | 1504.8 | 12.31ms | 16.51ms | 22.20ms | 30.49ms | 201 × 500 |
| **50** | **2333.3** | 19.58ms | 30.44ms | 39.22ms | 48.26ms | 201 × 500 |
| 100 | 2173.3 | 42.21ms | 62.85ms | 80.71ms | 104.75ms | 201 × 500 |
| 200 | 2149.6 | 82.61ms | 128.32ms | 185.18ms | 212.80ms | 201 × 500 |

**怎么读这张表**：

- **吞吐在并发 50 附近到顶**（2300/s），并发 100～200 不再涨 —— 到了**排队区**：
  并发越高，单个请求等得越久（p50 从 19.6ms 涨到 82.6ms），但总吞吐不变。
  **这是好事**：说明瓶颈不是「扛不住」，而是「已经饱和了，再加并发只会加延迟」。
- **错误率全程 0**：六轮 3000 张票，全部 201，没有一次 5xx、没有一次池空。
- **防重投始终正确**：每轮 5 次同 nullifier 并发提交，**恰好放行 1 个**，
  其余 4 个拿到 409 `DOUBLE_VOTING`。

**领取链路与投票链路的单请求耗时**（服务端自己测的，3535 次请求的均值）：

| 请求 | 均值 | 说明 |
|---|---|---|
| `credentials/eligibility-challenge` | 4.18ms | 签发挑战（无状态） |
| `credentials/claim` | 36.46ms | 验资格证明 + 预留槽位 + 记资格使用 |
| `credentials/blind-sign` | 21.14ms | RSA 盲签名（实测签名本身 1.92ms） |
| `credentials/attest` | 20.29ms | 验签 + 落库 |
| `votes` | 27.35ms | 验 Groth16 证明（实测验签本身 0.80ms）+ 落库 |

**一个投票人的完整成本** = 领取 4 步（81.9ms）+ 投票（27.4ms）≈ **110ms 的服务端时间**。

## 5. 服务端内部视角

### 5.1 密码学（实测）

| 操作 | 耗时 | 在哪一端 |
|---|---|---|
| 选票出证明（7917 约束） | **23.8ms** | **客户端**（投票人的浏览器） |
| 选票验签 | **0.80ms** | 服务端 |
| 资格出证明（6860 约束） | 19～110ms | 客户端 |
| RSA 盲签名 | 1.92ms | 服务端 |
| RSA 凭证验签 | < 0.1ms | 服务端 |

**服务端最贵的一步是验签（0.8ms），客户端最贵的一步是出证明（23.8ms）。**
所以「算力不够」这件事，**先怀疑客户端**（浏览器），而不是投票服务。

### 5.2 数据库（实测）

| 项 | 实测值 |
|---|---|
| `SELECT 1` 往返 | 39µs |
| 一条走模型的查询 | 47µs |
| `INSERT` + 提交 | 75µs |
| 一个事务（2 条语句） | 243µs |
| 投票窗口内的并发连接 | **峰值 11 条**（64 条连接池里闲置着） |
| 锁等待 / IO 等待 | **零**（`pg_stat_activity` 里没有任何 `Lock` / `IO` 等待事件） |

**结论：数据库完全不是瓶颈。** 一次投票的服务端数据库成本约 **0.5ms**。

### 5.3 连接池：不要开大（本次最重要的配置结论）

| 池大小 | 第一轮吞吐 | 连跑多轮 |
|---|---|---|
| 16（**推荐**） | 2134～2333/s，**首轮即满速** | 5 轮稳定在 1909～2148/s |
| 64 | **307/s**（冷启动惩罚） | 2245～2304/s，之后连跑几十轮回落到 **1400/s** |

**原因**：64 条连接要现场建 **64 个 PostgreSQL 后端进程**（每个约 38 MB），
既拖慢启动，又挤占内存；而投票写路径每请求只占连接约 0.5 ms，
**16 条连接的理论上限已是 3 万+/s** —— 远高于实测的 2300/s。

**所以**：`db.max_open_conns` / `db.max_idle_conns` 配 **16** 即可
（`configs/config.production.yaml` 已经是这个值）。

⚠️ **另一个极端更糟**：不配（默认 0）时 `database/sql` **只保留 2 条空闲连接**，
高并发下每个请求都要重开一条数据库连接 —— 量到的是连接开销，不是服务端能力。

### 5.4 CPU

投票窗口内服务端只用到约 **1 个核**（28 核的机器）。
整机 CPU 在压测期间是 99～100% —— **但那是被压测客户端吃掉的**（它在一台机器上
出几百份证明）。真实部署里客户端在投票人自己的机器上，**服务端侧会非常闲**。

## 6. 领取路径（一人一票）

- 本次测量共发起 **3535 次凭证领取**，**全部 201，零「池空」**。
- 服务端内部按路由统计：`claim` 3535 次全部 201（见 §4 的表）。
- ⚠️ **这一项在修复前是坏的**：原先的槽位分配不是原子的，并发领取会抢同一个槽位，
  重试耗尽后**池里明明还有几十上百个空槽位却报「池空」**。修复走的是
  PostgreSQL 的 `FOR UPDATE SKIP LOCKED`（见 `docs/project-map.md` 陷阱 13）。
- **凭证池的槽位数要 ≥ 投票人数**：一人一票，池子不够就有人领不到票。
  （池空时客户端拿到 409 `CREDENTIAL_POOL_EMPTY`，**不重试**。）

## 7. 已知偏差

| 偏差 | 方向 | 说明 |
|---|---|---|
| **客户端与服务端同机** | **低估服务端** | 压测客户端在投票窗口里也在抢 CPU（28 核共享）。真实部署里客户端在投票人的机器上，**服务端的真实能力比这组数字高**。 |
| 客户端出证明**不在**测量窗口内 | 不影响服务端数字 | 出证明是客户端的成本，服务端只验签。 |
| Windows + PostgreSQL | 可能低估 | Linux 上 PostgreSQL 的进程模型与文件 IO 更友好；本报告只对「Windows + PG 17.7」这一组合负责。 |
| 单机单副本 | — | 多副本的线性度未测（限流是**进程内**的，多副本时实际额度 = 配额 × 副本数）。 |
| 名单规模 512 人 | — | 资格电路的树深是**编译期常量** 10，单份名单上限 1024 人（见 §3.5）。 |

## 8. 怎么复现

```bash
# 需要一个已经存在的 PostgreSQL 库（脚本不建库）
export PG_HOST=127.0.0.1 PG_USER=postgres PG_PASSWORD=... PG_DATABASE=anonvote_capacity
export MEMBERS=512          # 名单成员数，必须 ≥ VOTES + DUPLICATES（一人一票）
export VOTES=500            # 每轮投票数（别低于 500，见 §3）
export CONCURRENCIES="1 5 20 50 100 200"

bash ./scripts/capacity-run.sh setup    # 建密钥、生成名单、迁移、起 release 模式服务端
bash ./scripts/capacity-run.sh sweep    # 并发扫描
bash ./scripts/capacity-run.sh stop     # 收尾
```

**报告里的数字都是 `sweep` 直接产出的 JSON**（`.capacity/reports/report-c<并发度>.json`），
可以用 `jq` 复核。
