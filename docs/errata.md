## E1 · v0.1.0：「v0.1.0 的 v1 密文会被 v0.1.0 拒绝」

| 项 | 内容 |
|---|---|
| 影响范围 | **仅文档措辞。** v0.1.0 的代码、5 个平台二进制、门户产物与各附件的 sha256 全部有效，无需重新下载或重新发布 |
| 涉及文件 | tag `v0.1.0` 源码树中的 4 个文件、7 处陈述（见下表） |
| 错误陈述 | 「v0.1.0 的旧密文（v1 格式）会被直接拒绝」「与 v0.1.0 的密文不兼容」 |
| 正确陈述 | **v0.1.0 自身即 v2 密文格式。** 被直接拒绝的是 **v0.1.0 之前**产出的 v1 格式密文 |
| 为什么会错 | T7（密钥派生改 HKDF、密文格式升 v2，提交 `a036a9b`）**落在 v0.1.0 tag 之内** —— `git tag --contains a036a9b` 返回 `v0.1.0`，且 tag 里的 `kyber_elgamal.go` 已经是 `kyberCipherVersion = byte(2)`。写文档时把「T7 之前的旧密文」写成了「v0.1.0 的旧密文」：版本号本身被当成了它自己的对象 |
| 实际后果 | 会让人以为「从 v0.1.0 升级会丢旧选票」。就 v0.1.0 自身而言不存在这个断点 —— v0.1.0 产出的密文能被 v0.1.0 正常解密。⚠️ **注意**（2026-10-25 补）：这条在写下时还带一句「v0.1.0 与 v0.2.0 之间没有已知的密文格式不兼容」，**那句话到 v0.2.0 已被证伪** —— v0.2.0 的选票密文从 v2 升到 v3（零知识电路要求 BN254 标量域），**v0.1.0 的旧密文在 v0.2.0 里解不开**。见 `docs/release-plan-v0.2.0.md` §3 |

### 已做的处理

1. `main` 上这 4 个文件全部更正（提交 `4c07cfb`），并把 v0.2.0 发版清单里那条
   「必须写明与 0.1.0 的密文不兼容」改成条件式。⚠️ **该条件式已被 v0.2.0 推翻**
   （2026-10-25 补）：v0.2.0 最终**确实改了密文格式**（v2 → v3），并已在
   `CHANGELOG.md` 的 0.2.0 段与 `docs/release-plan-v0.2.0.md` §3 写明不兼容。
2. **tag `v0.1.0` 保持原样，不移动。** 已发布版本的 tag 不可变；产物来源的可追溯性
   优先于改一句措辞。需要历史版本时用 `git show v0.1.0:<file>` 取原文即可。
3. GitHub Release v0.1.0 的正文加勘误指引 —— 顺带说明：Release 正文本身的技术表述
   **原本就是正确的**（「与 v0.1.0 之前的 v1 格式不兼容」），错的是随源码分发的
   CHANGELOG 与 `docs/` 里的那 4 个文件。

## 新增勘误的规矩

1. 只记**已发布版本**里的错误陈述；`main` 上还没发出去的改动不算勘误，直接改。
2. 每条必须写清：影响范围（是否涉及代码/产物）、正确陈述、为什么会错、实际后果。
3. 勘误只改文档与说明，**不动已发布的 tag、不重发产物**。若将来真的出现影响产物
   的问题，那是发 `v0.1.1`，不是改 v0.1.0。
4. 登记后同步三处：本文、`CHANGELOG.md` 对应版本段、GitHub Release 正文。
